# Durable native session storage

`SessionStore` stores owned native projections in a private SQLite database. Node uses its built-in SQLite API and requires Node 22.13 or later without experimental flags. Bun uses its own built-in SQLite API. Runtime selection is explicit; a missing backend fails with `SESSION_STORE_RUNTIME_UNAVAILABLE`. The store adds no native package dependency.

The database scope binds the canonical project directory, host contract and native contract versions. Opening it under a different scope fails; a format change requires an explicit migration rather than erasing older state. The database and SQLite sidecars must be private, regular, singly linked files owned by the process user. The private directory and database inode remain checked during use. Symlinks, changed ownership or changed safety boundaries reject before an operation can publish state.

`load(sessionID)` returns an immutable receipt and JSON payload. `save(receipt, payload)` accepts only a receipt issued by the same store. A transaction checks its session revision before updating data, so a stale writer cannot replace a newer accepted projection. The payload is copied before asynchronous work; its checksum and stored byte length are verified on read. No hook is executed by loading or saving state.

Deletion publishes a tombstone. Tombstone retention is bounded, and a global generation guard prevents an old absent-state receipt from recreating a deleted row after its tombstone is pruned. Live session and aggregate payload quotas are checked in the same write transaction. Oversized state fails explicitly without truncation or replacement of the previously accepted payload. The defaults permit a payload up to 32 MiB, retained live payloads up to 256 MiB and up to 1,024 live sessions; retained tombstones have a separate bound equal to the configured session limit. SQLite file growth also has a page budget.

Disposal rejects new operations, drains accepted work and closes the connection while retaining durable records. Session deletion and runtime disposal therefore have distinct data lifetimes. Failure diagnostics identify operation, session, outcome, correlation ID and elapsed time without payload contents or storage paths. Failed diagnostic observers are counted separately.

Native history consumers must validate their own snapshot shapes, restore original IDs and timestamps, bind restored state to the new session lifetime and await required checkpoints before externally visible effects. A durable store alone does not establish native resume conformance or recover original tool input that was discarded before the plugin observed it.

Startup and prompt record snapshots retain native attachment bodies, model rendering, execution timestamps, record IDs and prompt bindings. Startup snapshots also preserve the failure fingerprints used to suppress repeated nonexecuting failures on resume, and unbound startup batches remain unbound until an accepted prompt supplies their binding. Prompt snapshots preserve original prompt fingerprints and distinguish unobserved history from an observed history with no attachments. Restore rejects foreign sessions, duplicate IDs, inconsistent rendering and exhausted quotas before publishing any restored records.

The V1 transcript codecs include original tool inputs with their tool, turn and call ownership. Claude snapshots retain captured model dates; Codex snapshots retain startup context timestamps and journal history guards. Filesystem paths for temporary transcript files are not restored: a fresh owned file is produced from validated host history and the retained native records. A failed aggregate restore rolls back its admitted component state. The V1 codec rejects V2 state explicitly rather than omitting Stop records.

The V1 prompt-context codec retains accepted user positions and attributed context independently of the active source configuration. It does not retain request tickets or provider layouts; the new runtime must verify the host layout before issuing a fresh request ticket. Historical entries do not acquire ownership of a new active turn, and session closure removes their in-memory state.

The default V1 binding loads owned state before startup, prompt, tool and model use. It saves captured original inputs and native transcript observations before command hooks can execute, saves admitted startup and prompt records, and saves model dates before model requests. Default observation retains raw tool input even when a source has no tool registrations. Caller-supplied transcript services keep their own snapshot ownership; the default store preserves existing payload fields for those services without restoring or overwriting them.

Storage lives beneath `XDG_STATE_HOME`, falling back to `$HOME/.local/state`, in `opencode-harness-hooks/<canonical-project-hash>/native-state`. A new activation regenerates temporary transcript files from host history and retained owned snapshots. It never executes historical hooks to reconstruct state. A real session-deletion event removes the durable payload through a tombstone; closing an in-memory session or disposing a plugin retains durable state for another activation.

Provider composition discovers retained prompt context through a bounded scan of immutable, checksum-verified session receipts. This keeps earlier context available when the active source selection no longer contains prompt hooks. The scan executes no hooks and restores no active session; an authentication loader is wrapped when selected or retained context requires projection. A fresh tool-only composition with no retained context preserves its original authentication loader.

The registered `claude.session.resume` and `codex.session.resume` comparisons independently resume the pinned native harness and restart a stock V1 server. They verify retained session identity, transcript prefix and historical original shell input after a rewrite, alongside current pre/post input, side effects and model-result controls. Default-factory tests separately cover mixed startup/prompt context, selection changes, blocked-first-prompt recovery, cancellation ownership and deletion. These checks do not establish compaction, arbitrary pre-plugin history, every artifact or V2 persistence parity.

Prompt admission precedes the host's own conversation write. Durable checkpoints retain pending prompt identities until another activation confirms them against the host's saved user-message IDs. If a pending prompt was never saved and has no observed model or tool activity, restoration withdraws its prompt records and context and releases its startup bindings for the next accepted prompt. Missing host history with observed model or tool activity fails explicitly. Reconciliation does not delete confirmed historical prompts or infer that pruned history was an unsaved admission.
