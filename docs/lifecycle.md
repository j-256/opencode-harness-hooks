# Session lifecycle reference

The default V1 binding delivers the documented [startup context, artifacts and environment subset](v1-startup-assessment.md). Its session-created observer is joined by awaited prompt/tool/model barriers. The V2 factory still requires separate lifecycle integration. Cold reconstruction, additional events and remaining native effects are pending implementation; the native fixtures below remain independent reference evidence for those branches.

## Core startup coordination

`createRuntime` accepts an explicit `RuntimeServices.sessionStart` integration. Its required `admit` callback receives the immutable startup event, shared session snapshot, attributed dispatch, optional environment-file plan and cancellation signal. The callback must apply the native context, artifacts and controls, or reject an effect it cannot support. Completing that callback admits the occurrence; a callback which discards effects does not establish compatibility. An `environmentDirectory` is required when selected Claude commands need `CLAUDE_ENV_FILE`.

Call `runtime.start(event)` from a verified host boundary with `host`, `event: "SessionStart"`, `sessionID`, `activationID`, `cwd` and explicit native metadata in `data` or `dialectData`. Each configured dialect needs its actual source value. Matching handlers which can execute have their complete payloads preflighted before session state, environment files or commands are created. Native skips keep their skip reason. Native prompt, agent and MCP rejections carry private `nativeFailureArtifact` records for admission without invoking those services. Nonexecuting handlers do not demand unused payloads or services. Model, permission and transcript requirements follow the source dialect; any supplied artifact must already be compatible with its native consumer. The coordinator does not infer startup versus resume from empty history or create transcript content.

The opaque `activationID` identifies one delivered occurrence. Repeated delivery with equivalent metadata joins its pending work or retained receipt; object key order is immaterial, while array order and field values remain significant. Conflicting or stale delivery fails explicitly. A distinct activation runs all matching registrations again, including identical commands and sources from both dialects. This routing identity is separate from native per-handler `once`, reset and repeated-context suppression semantics, which remain conformance work. Overlapping occurrences for one session produce `HOST_SESSION_START_OVERLAP_UNVERIFIED`; separate sessions can run concurrently.

`runtime.waitForStart(sessionID)` joins startup. Prompt and tool preparation wait for admission, while model observation rejects an unfinished barrier. Startup uses session lifetime rather than user-turn cancellation, so replacing a prompt can cancel its waiter without killing startup. Session closure and runtime disposal cancel pending startup. Admission services must honor cancellation before committing effects. Disposal tracks the underlying admission promises, reports `HOST_SESSION_START_ADMISSION_DRAIN_FAILED` if they remain pending beyond the service timeout, and permits a cleanup retry after they settle. An undrained admission retains overlap protection for that session even after timeout. Disposed runtimes reject later deliveries. Sources without startup registrations acquire no barrier from an unused service. Activation services, command environment and native event data are captured before asynchronous work can observe caller mutation.

Retained receipts contain identity, dispatch correlation and outcome counts rather than raw dispatch output. Failed admission remains terminal for that occurrence and cannot silently replay command side effects. Input and receipt retention have explicit bridge limits; `maxActivations` controls retained occurrences. `serviceTimeoutMs` bounds environment-file preparation and host admission without replacing native handler deadlines. Diagnostics identify phase, activation, dispatch and missing source/registration fields without commands, outputs, native payloads or local paths. Observer failures are counted separately from native execution.

V1 supplies the default admission and shell binding described in the startup guide and accepts an explicit core startup service when the consumer owns admission. V2 retains `HOST_SESSION_START_HOST_UNAVAILABLE` until its factory binding is implemented. Cold source classification, precise timing across all activation paths, native artifact/context reconstruction and durable host-side application remain acceptance work.

## Environment-file ownership

`ClaudeEnvironmentFiles` from `opencode-harness-hooks/core` reserves separate file paths for an ordered selection of Claude `SessionStart` command registrations. The constructor receives `{ directory, sources }`, with the complete reviewed `LoadedSource` snapshot. Its `prepare(sessionID, registrations, signal)` method accepts the matching commands and returns an immutable plan with ordered `files` and a `registrationContext` map for command dispatch. Hook commands receive their own `CLAUDE_ENV_FILE` through that map. Source-level plugin data, options and shell selection remain in `HostServices.sourceContext`.

The caller supplies an absolute, dedicated state directory and preflights native payload metadata before executing hooks. The service creates private directories, hashes the session identity in paths, binds the complete Claude source snapshot in a bounded manifest, and leaves new hook files absent until commands write them. Concurrent activations can reserve the same snapshot without overwriting each other's manifest. A fresh process recovers the same ordinal paths and preserves appended code for session-ID resume. Different startup/resume matchers can select different registrations or change the selected count; paths follow that activation's configuration order, and files from an earlier, larger selection remain present. The service leaves their code opaque; it does not parse exports or execute shell content.

Construction bounds source snapshot sizes and captures reviewed registration signatures. Preparation bounds the selected registrations and identity sizes, rejects unreviewed or reordered commands, checks directory ownership and private permissions, and rejects existing hook-file symlinks, hard links and special files. These are explicit bridge resource limits. Cancellation does not delete persisted files. The host owns the dedicated directory's retention policy; the service does not impose a disk quota or remove resume state on activation shutdown. These checks support POSIX hosts. Windows integration remains unsupported.

A changed Claude source snapshot for an existing session produces `ENVIRONMENT_LAYOUT_UNSUPPORTED`. Native reload, transcript-path resume namespaces and storage retention require further lifecycle integration and native comparison. Passing a file plan into `dispatchEvent` verifies hook-process ownership only. It does not establish startup barriers, context placement, tool-shell capture timing or replay parity, and it does not remove the default package's lifecycle capability gate.

## Native startup and resume

The pinned Claude Code headless fixture starts concurrent command handlers and gives them different completion delays. Startup context follows completion order, appears in native `SessionStart:startup` attachment records before the first user record, and reaches the model as user-role reminder blocks. The first submitted prompt and model request wait for the startup batch in this exercised headless flow. The fixture repeats the checks with `source: "resume"` and the corresponding native record label.

Each handler receives a distinct `CLAUDE_ENV_FILE` path in configuration order. On startup, the path is reserved before the file exists. Shell commands replay environment code in configuration order, so a later configured handler can override an earlier handler's value even when it completed first. Executable shell code and functions survive; reducing these files to parsed assignments would lose behavior. Repeated shell commands each evaluate the captured code, and their temporary shell state does not accumulate across commands in the fixture.

The fixture interleaves HTTP, prompt, agent, MCP and tool-conditioned handlers before the executing commands. HTTP startup hooks receive no request and create no attachment. Prompt, agent and MCP startup hooks do not execute but produce native `hook_non_blocking_error` attachments, even with `onFailure: "block"`. Their records have no rendered content and do not reach the model. A tool condition suppresses the handler and its failure attachment at this non-tool event. The fixture checks the exact error text, command and duration field presence, shared batch identity and record order. Executing command files still begin at ordinal zero; nonexecuting handlers do not reserve gaps in the environment-file ordinals.

Prompt and agent rejection durations are measured nonnegative millisecond values, including for rejection before model execution. They are not a literal zero contract. MCP rejection records omit that field. The fixture compares the remaining fields exactly and validates measured timing separately. Its non-timeout commands have a budget longer than the deliberate ordering delays; explicit timeout conformance belongs to the [native artifact fixture](transcripts.md#native-oracle-and-reader-verification).

When the same rejected handlers are selected again on resume, this fixture retains the original failure records without attaching them again. Its success records still appear for the resume batch. The fixture checks the retained record identities and absence of new failure records explicitly. Native repeated-record suppression and its interaction with changed handlers remain required artifact-admission work; returning a handler failure alone does not reproduce that behavior.

During startup, the fixture changes a variable in the same environment file from a prompt hook, the provider and the first pre-tool hook. The first shell command observes the pre-tool value. An edit made during that command remains present in the file but is not reflected by the second command. A separate append side effect still runs for each command. This establishes repeated execution of captured contents, rather than rereading a changed file for every command. Other cache invalidation events remain separate conformance cases.

Resuming by session ID reuses the existing environment files, and the resume hooks append another copy of their code. The fixture observes both copies executing for each command and the new generation taking effect. Resuming by transcript path retains the transcript session ID but allocates a new environment-file directory. Shell commands in that pinned capture nevertheless observe the previous activation's generation and its edited variable, even though the resume hooks wrote to the new directory. The fixture checks and reports both behaviors explicitly; a fresh pathname does not establish fresh environment consumption. The underlying cache mechanism and other resume flows require separate evidence. The persisted variables do not enter later hook processes, and events without environment-file support do not receive `CLAUDE_ENV_FILE`.

The `fewer` and `more` selection modes use separate startup/resume matcher groups. Session-ID resume reuses selected ordinals, preserves files from handlers omitted on resume, and incorporates a newly selected ordinal when the selection grows. The shorter-selection fixture proves that an earlier file still contributes to shell execution even when its handler does not run again. Transcript-path resume allocates fresh files for the selected handlers while commands continue to observe the prior namespace's generation in these pinned captures.

The native reference is [Claude's SessionStart contract](https://code.claude.com/docs/en/hooks#sessionstart). Its interactive startup behavior, other startup sources, extra native control fields, other environment-file events, Windows and PowerShell remain separate conformance cases. The fixture does not infer those behaviors from its headless startup/resume capture.

## Reproduction

From a repository checkout:

```sh
npm run test:native:claude:lifecycle -- --binary /path/to/claude
npm run test:native:claude:lifecycle -- --binary /path/to/claude --resume-mode path
npm run test:native:claude:lifecycle -- --binary /path/to/claude --selection-mode fewer
npm run test:native:claude:lifecycle -- --binary /path/to/claude --selection-mode more --resume-mode path
```

The command requires Node.js, POSIX process groups and Claude Code 2.1.318. It uses isolated HOME/config/project state, unchanged generated synthetic hook configuration and a loopback provider with synthetic credentials. It requires no package build or model account and installs nothing. `-h`/`--help`, `-b`/`--binary`, `-r`/`--resume-mode`, `-s`/`--selection-mode` and `CLAUDE_BINARY` are supported. Resume mode defaults to `id`; `path` exercises the separate transcript-import behavior. Selection mode defaults to `stable`; `fewer` and `more` shrink or grow the selected handler set on resume and can be combined with either resume mode. Temporary state is removed on completion or failure.

Metadata-only JSON reports the exercised native properties, `bridgeLifecycleComparison: "not-implemented"` and `equivalent: false`. It excludes source commands, output, environment values, local paths and provider traffic. Exit statuses are `0` for the native fixture checks, `1` for runtime/check failures, `2` for usage/version/platform preconditions and `3` for missing dependencies. A native-only success does not satisfy the required bridge or migration acceptance gates.
